### Adjustment System Project Plan (2).pptx
These rules will be applied to the Global Adjustment Maintenance UI.
Adjustment Detail
Pulling in item classes should be automated.
Only “end item” item classes should be pulled in. (AS400 Table: AENDCLS)
Is the data replicated to SQL? Do we need an API?
User should be able to enter a default setting for calculation type, value, order from date, and order to date as the item classes are pulled in. User can modify after the fact.
User should be able to set the default based on Import/Domestic, Product Line Code, Sales Category, Division Code, Retail Category, or Financial Division. (All defined in AENDCLS)
There should be a
control table
containing all valid
Calculation Types
and the min/max values acceptable.
It should only be maintainable by IT.
For MVP, only one entry will be present.  Development in the microservice will be necessary before adding any future options.
MVP: Calculation Type = “Percentage”; Minimum Value = 0; Maximum Value = ?;
The UI will provide edit checks to support the min/max values.
Calculation type can be maintained until the earliest “From” date has passed. Then the field should no longer be maintainable.
Value can be maintained until the earliest “From” date has passed. Then the field should no longer be maintainable.
There should be a
control table
containing the
Time Fence
in days.
It should only be maintainable by IT. (start with 7 days in all 3 time fences)
It should have a “From” time fence, a “To” time fence, and a “Recalculate” time fence
Order From Date must be outside the “From” time fence. (It must be x days greater than the current date)
The Order From Date is not maintainable once it is inside the “From” time fence. (Less than x days greater than the current date)
Order To Date must be greater than the Order From Date and greater than the “To” time fence.
This date is not maintainable once it is inside the “To” time fence. (It must be x days greater than the current date)
If maintained, it must remain greater than the from date and outside the “To” time fence.
Invoice From/To Date are not functional in MVP.
They should be allowed to remain unset.
If set, Invoice From/To should follow the same rules as order From/To date respecting time fences.
Recalculate Date is not functional in MVP.
If set, Recalculate Date must be outside the “Recalculate” time fence and greater than or equal to both the Order From Date and Invoice From Date if set.
At record creation, the creation date/time/user should be updated and the last change date/time/user.
Upon update, the last change date/time/user should be updated.
Active Code: all records will be active upon creation.  They can be set to inactive by the user only if neither from date has passed. Once a from date has passed, the user can only maintain the to dates. Once the to dates have passed, then the record can be set to inactive if desired.
Global Adjustment Maintenance Rules

### Adjustment System Project Plan (2).pptx
These rules will be applied to the Global Adjustment Maintenance UI.
Adjustment Detail – Customer Override
User should be able to set up a customer override for an adjustment
The override will be for a customer/”ship to” combination.
“ship to” will be blank for a “bill to”
There will be two options for overriding
The user can choose to “exclude” a customer/”ship to” from an adjustment
This excludes the customer/”ship to” from the entire adjustment (all detail records)
The user can choose to customize the detail settings for a customer/”ship to”
This option will pull the detail settings for the given surcharge into the override table for the customer/”ship to” and allow the user to maintain the Calculation value and dates.
ALL rules for the dates on the detail UI will also be enforced on the override UI.
At record creation, the creation date/time/user should be updated and the last change date/time/user.
Upon update, the last change date/time/user should be updated
Active Code: all records will be active upon creation.  They can be set to inactive by the user only if neither from date has passed. Once a from date has passed, the user can only maintain the to dates. Once the to dates have passed, then the record can be set to inactive if desired.

Each service is responsible for a single feature and has its own technology stack, including a database and data management model.

Issue
Issue:
Global container shipping rates are drastically increasing in response to approximately 30% of the global container shipping capacity being taken off-line.
Opportunity:
Need to add an Import Surcharge to imported products to offset the additional costs. If nothing is done the impact of the increased container costs will continue to impact profits.
Objective:
Create a solution that enables a surcharge to be applied to invoices with maximum visibility and flexibility to both new orders and open orders.

API URL

Last Call date of this API

Destination table location

### Adjustment System Project Plan (2).pptx
Microservice Private Data Sync APIs
The microservice data sync APIs will be located along side the microservice API.
There will be 3 Adjustment APIs: Header, Detail, Override
Each API will receive the last run parm.
Each API will call its respective counterpart in AshleyNET passing the last run parm.
The return data set will be all
changed
records for the respective table since the last run date/time.
The API will then sync (update/add) the data set returned with the respective private data table.
Note that calls to the microservice will be ongoing so there can be no outage of data.
Finally, the API should remove all records flagged as inactive.
There will be a Product Data Sync API to sync Product Data into the private data
The API will receive the last run parm.
The API will call the PIM Product Data API in the PIM system with the last run date to retrieve changes since the last run date.
Include Item List = True
Multiple Environment Item List = True
The API will update the private data with changes.
