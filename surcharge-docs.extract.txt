
### ADJUSTMENT MICROSERVICE SOP (1).docx
Adjustment Microservice SOP
Production URL:
https://adjustment-microservice.prod.finance.ashleyfurniture.com/Adjustment/Orders
Stage URL:
https://adjustment-microservice.stage.finance.ashleyfurniture.com/Adjustment/Orders
The caller should call the microservice in a way that it responds with the value needed.
Example 1: if the caller needs the surcharge for the entire line-item quantity, then pass in the line-item quantity and the line item extended base price. The surcharge returned will be the extended surcharge for the quantity given.
Example 2: if the caller needs the surcharge for a single item (quantity 1) then pass in the quantity of 1 or no quantity and the base price for 1.  The surcharge returned will be for a quantity of 1.
Input Field Definitions
Order Level (one per order. May have multiple orders per call)
Order ID:
Entry: Optional
Format: String
Customer:
Entry: Required
Format: String
Ship To:
Entry: Required
Blank is a valid shipto
Format: String
Order Date:
Entry: Required
Format: ISO 8601
Estimated ship to:
Entry: Optional
Format: ISO 8601
Invoice Date:
Entry: Optional
Format: ISO 8601
Warehouse ID:
Entry: Optional
Format: String
Item Level (one per item on this order. May have multiple items per order)
Item ID:
Entry: Required
Format: String
Quantity:
Entry: Optional
Quantity of 1 will be assumed if not provided
Format: Numeric
Price:
Entry: Required
Should be the total price for the quantity given
If no quantity is given, this should be the price for 1
No unit of measure necessary
Format: Numeric
Output Field Definitions
Order Level (one per order submitted)
Order ID:
Return:  Input value
If no field is passed then the return is blank
Format: String
Customer ID:
Return: Input value
Format: String
Ship To:
Return: Input value
Format: String
Total Surcharge:
Return: Sum of all surcharges for this order
Format: Numeric
Adjustments Level (one per item submitted this order)
Item ID:
Return: Input
Format: String
Quantity:
Return: input
If no field is passed or if the value is passed as null then the return value is set to 1
Format: Numeric
Price:
Return: Input
Format: Numeric
Status:
Return: 0=API OFF, the API check switch is set to off
Return: 1=NONE APPLIED, no Adjustments applied for this item
Return: 2=APPLIED, Adjustments applied for this item
NOTE: If 0 or 1, no adjustment details will be sent for this item
Format: String
Adjustment Details (can be multiple per item)
Credit Code
Return: Credit Code associate with the adjustment
Format: String
Adjustment Name:
Return: Name/Description of adjustment being applied.
Typically: credit code concatenated with its description
Format: String
Adjustment Amount:
Return: calculated dollar amount of this adjustment for the quantity given
Format: Numeric
Invoice level:
Return: 1= the adjustment should be applied on the line-item level
Return: 2= the adjustment should be applied on the Order level
Format: String (Character value for maximum flexibility)
Taxable:
Return: Y=yes; N=no
from the credit code
Format: String
Commissionable:
Return: B=INVOICE & CM; I=INV only; N=Neither
from the credit code
Format: String
Quantity:
Return: input
If no field is passed or if the value is passed as null then the return value is set to 1
Format: Numeric
Calculation value:
Return: number value used in calculation
example: 2 (indicating 2% when the calculation type is percentage)
Format: Numeric
Calculation type:
Return: type of calculation performed
example: “Percent”
Format: String
Applied level:
Return: attribute used to qualify for adjustment
example: “ItemClass”
Format: String
Applied Level value:
Return: attribute value
example: “ZABC”
Format: String
Charge:
Return: true or false
True = this is a charge that will increase the invoice amount
False = this is a credit that will decrease the invoice amount
Format: Boolean
JSON Definition
Type of call – POST
Swagger documentation(technical) for this microservice
https://aazeus-fnprwb01.ashleyfurniture.com/AdjustmentAPI/swagger/index.html

Introduction
Introduction
With global container shipping capacity reduced by 30%, freight rates have surged, threatening profit margins on imported goods. To counter this, a dynamic Import Surcharge mechanism is proposed. This solution ensures that surcharges are applied fairly and visibly across both new and open orders, with centralized control and customer-level flexibility.
Core Functionalities
1. Global & Customer-Level Management
Global Configuration: Centralized surcharge settings by Item Class.
Customer Overrides: Ability to exclude customers or apply custom surcharge percentages.
2. Surcharge Table & Item Class Mapping
A dedicated surcharge table maps applicable Item Classes to:
Surcharge percentage (x%)
Effectivity dates (based on order date)
Future-ready for additional levels: Sales Class, Warehouse, Item, etc.
3. Calculation Logic
Line-Item Based: Surcharge = Unit Price × % Surcharge
Rounding: Rounded up to the nearest dollar.
Quantity Handling: Extended based on quantity ordered.
Live Recalculation: Until shipment/invoicing, surcharge is recalculated dynamically.
Non-Commissionable & Non-Taxable: By default, with future options to enable both.
4. Invoice Presentation
Machine-to-Machine: Surcharge is rolled into the line-item price.
Human-Readable: Surcharge appears as a separate line item for clarity.
5. Future-Proofing
Support for:
Flat rate, cube, or weight-based surcharges
Invoice-date-based effectivity
Recalculation triggers for open orders
Refundable surcharges
Commissionable and taxable options
Order-level surcharge aggregation

Surcharge Microservice – Processing Workflow
Here’s how the microservice incorporates customer overrides during its execution:
1. Item Parsing
For each order line, extract:
ItemNumber
CustomerId
ItemClassCode
OrderDate
2. Override Lookup
The microservice queries the CustomerOverride table to check if:
A record exists for the given CustomerId and ItemClassCode
The current OrderDate is within the specified date range
The AdjustmentDetailId maps to a valid AdjustmentHeader, which holds the actual CreditCode
3. Credit Code Mapping
Each override is indirectly linked to its CreditCode through:
CustomerOverride → AdjustmentDetail → AdjustmentHeader
This chain allows the microservice to validate the percentage override within the context of the business adjustment category.
4. Surcharge Decision
If a matching customer override exists:
Use the custom percentage from the override
If not:
Fallback to the default rule in AdjustmentDetail

Data Flow Process:
Input Processing:
System receives Order ID, Customer ID, and Ship To
Validates against Header table for active adjustments
Calculation Flow:
Checks Adjustment Header for active records
References Adjustment Detail for calculation rules
Verifies Customer Override for exceptions
Applies appropriate calculation type and value
Output Generation:
Compiles all calculations at item level
Accumulates total surcharge at order level
Returns complete adjustment details with appropriate status codes
The rightmost columns (A7, P80, etc.) appear to be field specifications for length and type of data storage.
Starting Point
"Receive Parms": System gets input data (like order details, customer info)
"Check Switch": Checks if the service is ON or OFF (like a light switch)
Initial Decision
If switch is OFF → "Return level 0" (service doesn't process anything)
If switch is ON → Continues to next steps
Main Process Flow (when ON)
First retrieves all product data for the items in the order
Runs calculations for each order/item
Checks for any Item Class Adjustments (like import surcharges)
Data Sources (shown in right side boxes)
The system uses four private databases:
Product Data (item information)
Header Data (adjustment rules)
Detail Data (specific adjustment details)
Override Data (customer-specific rules)
Future Planning
Shows placeholder boxes for "Future Adjustment" (system is designed to add more adjustment types later)
End Point
"Return Adjustments": Sends back the final calculated adjustments
Think of it like a decision tree where each step depends on the previous one, similar to:
Checking if a store is open (switch)
If open, looking up prices (product data)
Applying any special discounts (adjustments)
Calculating final price (return adjustments)
